# 数据库设计规范

## 1. 目的与基本原则
本规范用于指导数据库概念、逻辑和物理设计，保证数据模型一致、完整、安全且易维护。



## 2. 命名规范
1. 数据库对象默认使用小写英文和下划线分隔的 `snake_case`。
2. 表名、字段名应表达明确业务含义，避免拼音、无意义缩写和含糊名称。
3. 表名单复数风格应在项目中统一。
4. 主键默认命名为 `id`；外键采用关联实体名加 `_id`，例如 `user_id`。
5. 时间字段应明确表达含义，例如 `created_at`、`updated_at`。
6. 避免使用数据库保留字作为对象名称。
7. 命名规则一经确认，应在新增表和字段中保持一致。



## 3. 表与字段设计
1. 字段类型应准确表达数据含义，避免所有字段统一使用字符串或过大的类型。

2. 必填字段应设置 `NOT NULL`；仅在业务允许缺失时使用可空字段。

3. 默认值必须有明确业务含义，不得掩盖数据缺失或无效状态。

4. 金额等需要精确计算的数据应使用适合的定点数类型，避免浮点数误差。

5. 日期时间字段应统一时区策略；推荐 UTC 存储并在展示层转换，若采用其他策略须明确记录。

6. 状态字段应具有明确、有限且有文档说明的取值集合。

7. 不得将多个独立业务值拼接到一个字段，除非该字段确实表示不可拆分内容或采用明确约定的结构化存储。

   

## 4. 主键、外键与完整性约束
1. 表必须要设计主键，主键生成策略应在项目中统一使用自增主键，主键必须唯一、非空，并稳定标识一条记录。
2. 禁止使用物理外键，不得通过SQL、ORM 模型或数据库迁移创建 FOREIGN KEY 约束。
2. 表之间通过逻辑关联字段建立关系，由应用层负责关联校验和业务完整性维护。
4. 业务上必须唯一的值应使用唯一约束，而不应只依赖应用代码检查。
5. 数据完整性不能只依赖前端校验；服务端应校验输入，数据库约束应作为重要防线。
